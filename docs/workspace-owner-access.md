# สิทธิ์เจ้าของระบบในทุก Space

บัญชีใน Control Base ที่ `System Role=Owner` และ `Active=true` เข้าใช้งานทุก Space ที่เปิดอยู่ได้ในสิทธิ์ Admin โดยไม่ต้องรับคำเชิญหรืออนุมัติสมาชิกแต่ละทีม บทบาท Admin ปกติยังมีผลเฉพาะ Space ที่เป็นสมาชิก

## จัดการ Admin

1. Login ด้วยบัญชี Owner แล้วเปิด `/spaces` หรือกด **เปลี่ยน Space** จากหน้าทำงาน
2. เลือก **จัดการ Admin / สมาชิก** ของทีมที่ต้องการ
3. สำหรับคนใหม่ กรอกอีเมล Google เลือก **Admin** เปิด **อนุมัติให้ใช้งาน Space นี้** แล้วกด **บันทึกสมาชิก**
4. สำหรับสมาชิกเดิม กด **แก้ไขบทบาท** ที่แถวนั้น เลือก Admin แล้วบันทึก
5. เมื่อต้องการถอน Admin ให้เปลี่ยนเป็น Secretary/Agent หรือปิดสมาชิก ระบบป้องกันการถอน Admin ที่ใช้งานได้คนสุดท้าย จึงควรตั้ง Admin คนใหม่ก่อน

Owner จัดการสมาชิกของ Space ที่พักไว้ได้ แต่ต้องเปิด Space ก่อนเข้าหน้างาน การเปลี่ยนบทบาทนี้ไม่เปลี่ยนสมาชิกใน Space อื่น และไม่เปลี่ยนบทบาทเจ้าของระบบ ปุ่มแก้ไข/ปิดสมาชิกของ Owner ถูกปิดไว้; สิทธิ์ Owner จัดการจาก Control Base เท่านั้น

## การตรวจสิทธิ์และข้อมูล

- API ตรวจ `System Role` และ `Active` จาก Control Base ฝั่งเซิร์ฟเวอร์ ไม่รับสิทธิ์จากค่าบนหน้าเว็บ
- เมื่อ Owner เปิด Space ที่ยังไม่มีสมาชิก ระบบสร้างตัวเชื่อม Users ใน Base ของทีมนั้นเพื่อให้ประวัติและ linked records อ้างถึงผู้กระทำจริง ใช้ membership `Agent, Active=false` เป็นค่าพื้นฐาน พร้อม audit `owner-identity-linked`; สิทธิ์ Admin มาจาก Owner เท่านั้น
- ถ้ามี membership เดิม ระบบคงบทบาทและ Active เดิมไว้ แล้วให้สิทธิ์ Owner ทับเฉพาะขณะใช้งาน
- เมื่อถอน `System Role=Owner` คำขอถัดไปกลับไปตรวจ membership เดิม ตัวเชื่อมที่สร้างอัตโนมัติไม่เหลือสิทธิ์ Admin ส่วน membership ที่เคยอนุมัติโดยตรงยังมีผลตามเดิม
- ปิด Active ของบัญชีส่วนกลางระงับการเข้าถึงทุก Space ระบบยังตรวจ Base binding และปฏิเสธ Space ที่เตรียมไม่เสร็จหรือข้อมูลเชื่อมต่อไม่ตรง

รุ่นนี้ไม่เพิ่ม migration หรือฟิลด์ Airtable ใหม่ ทดสอบด้วย fixtures แยกจากข้อมูลจริง ทั้ง Owner ที่ไม่มีสมาชิก การเปลี่ยน Admin การถอน Owner การพัก Space และการป้องกันสิทธิ์ข้ามทีม
